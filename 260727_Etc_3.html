01

DGX라는 이름을 작은 상자에 붙인 이유

DGX는 원래 데이터센터·AI 연구소용 브랜드(서버랙에 여러 GPU를 연결해 대형 모델을 학습·추론하는 시스템)입니다. 그런데 젠슨 황이 “깐부 회동” 선물로 준 DGX Spark는 한 손으로 들 수 있는 크기에 DGX 이름을 달았습니다.

핵심은 크기 축소가 아님
단순히 “큰 모델을 책상에서 돌린다”를 보여주기 위한 게 아니라, AI 서비스를 만드는 환경 자체를 개인에게 가져오는 것. AI 앱을 소비하는 PC가 아니라 AI 서비스를 직접 만들고 실험하는 개발 장비입니다.
GB10Grace CPU(ARM 기반) + Blackwell GPU 결합
128GB통합 메모리 (CPU+GPU 공유)
LinuxCUDA 중심 Docker 컨테이너 기반

일반 PC는 CPU 메모리와 GPU 메모리가 분리(예: GPU 24GB면 24GB 모델만). DGX Spark는 CPU와 GPU가 하나의 메모리 공간을 공유(통합 메모리)해서 GPU 메모리만으로는 못 올리던 대형 언어모델(LLM), 비전 언어모델(VLM)도 올릴 수 있습니다.

🔢 통합 메모리 시뮬레이터
필요 VRAM(대략): ~140GB → 일반 RTX 24GB: 불가 / DGX Spark 128GB(양자화 시): 가능

03

데모 1: AI 블루프린트 – 서비스 전체를 로컬에서

블루프린트(Blueprint)는 예제 코드가 아니라 모델+컨테이너+API+DB가 묶인 레퍼런스 애플리케이션(참고용 완성 서비스)입니다.

영상에서 사용한 것은 VSS(Video Search and Summarization) – 영상 파일을 넣으면 객체·행동·상황을 분석하고 자연어로 장면을 검색·요약하는 서비스.

docker 상태에 실제로 뜬 것들
• VSS UI (웹 화면)
• 영상 처리 서비스
• AI 모델 실행 서비스 (Vision 모델)
• 질문·요약 담당 Nemotron(네모트론, 엔비디아 LLM)
• 검색 결과 저장 Postgres DB
• Agent, API 서버
→ 하나의 프로그램이 아니라 6개 이상 컨테이너가 동시에 메모리·GPU를 점유하며 동작

안될공학 채널의 메타 관련 영상을 올려 “요약해줘” → 로컬 LLM이 요약. 파일 여러 개 중 “사람 등장 부분 스크린샷 해줘”도 수행. 로컬만으로 부족하면 클라우드 모델(Nemotron Super/Ultra, ChatGPT, Claude 등)을 API로 연결해 성능을 끌어올릴 수도 있습니다.

입력영상 파일들
처리비전 모델 + 임베딩
저장·검색Postgres + API
로컬: 모든 추론을 DGX Spark 내부 128GB에서 처리. 민감 데이터 외부 반출 없음, 비용 0원. 단, 초당 토큰은 서버보다 느림. 핵심은 “작은 시스템 안에서 완성된 서비스 구조가 돈다”는 검증.
04

데모 2: AI Workbench – 환경 지옥을 없애다

Workbench는 코드 에디터가 아니라 코드+모델+Docker 환경+라이브러리 설정을 프로젝트 단위로 관리하는 작업 공간입니다.

영상에서는 Agentic RAG(Retrieval-Augmented Generation, 문서를 검색해 답변하는 AI) 프로젝트를 클론(복사)해 실행했습니다.

  • 미리 구성된 프로젝트 선택 → 컨테이너·환경 자동 준비
  • 내 문서(안될공학 리서치 자료) 업로드 → 자동 임베딩(문장을 숫자로 변환해 검색 가능하게 만드는 작업) → 벡터 DB 구축
  • 로컬 모델 또는 NVIDIA foundation 모델(원격) 선택 → “최근 중국 AI 영상 내용 알려줘” 질문에 내 문서 기반으로 답변
경제적 포인트
직접 구축하려면 Python 환경, Docker Compose 설정, RAG 프레임워크·벡터 DB 연결, 임베딩 모델·환경변수 호환성 맞추기 등 수십 단계가 필요. Workbench는 이를 하나의 프로젝트로 묶어 환경 구성 시간(개발자가 가장 많이 낭비하는 비용)을 0에 가깝게 줄입니다.
💸 개발 비용 시뮬레이터: 클라우드 vs DGX Spark
클라우드 GPU(A100급 $3/시간): $240 / DGX Spark(전기료만): 약 $8
민감 데이터 외부 업로드 위험: 클라우드 높음 / 로컬 없음
05

데모 3: AI 에이전트 – OpenClaw + MCP

최근 AI는 답변을 넘어 파일 읽기, 프로그램 실행, 외부 서비스 호출로 확장됩니다. 이를 수행하는 것이 OpenClaw(오픈클러) 같은 에이전트.

에이전트는 MCP(Model Context Protocol, AI가 외부 도구를 호출하는 규약)나 API로 도구를 호출합니다. 하나의 에이전트를 띄우려면 모델 연결·권한·네트워크·실행 환경을 구성해야 하는데, 이를 관리하는 것이 NeMo(네모) 계열 프레임워크입니다.

온보딩에서 연결 가능한 것들
• NVIDIA Endpoint (자체 호스팅)
• Open Endpoint
• Google Gemini, Anthropic Claude 등 클라우드 모델
• 로컬 모델 (DGX Spark 내부)
→ 설치는 Jupyter 가이드로, VSS나 Workbench에서 만든 RAG도 MCP로 연결해 “VSS에서 사람 나온 장면 찾아서 RAG 문서와 연결해줘” 같은 호출이 가능
Blueprint – 서비스 구조 확인 (VSS: 영상→모델→DB→API)
Workbench – 내 문서로 RAG 프로젝트 제작
Agent (OpenClaw) – VSS·RAG를 MCP 도구로 연결해 에이전트가 호출
Scale – 필요시 DGX Station/서버/클러스터로 컨테이너 그대로 확장
06

경제 관점: 왜 엔비디아는 진입장벽을 낮추나

지금까지 AI 개발 중심은 데이터센터였습니다. 하지만 아이디어 검증·데이터 파이프라인·도구 호출 테스트까지 모두 데이터센터에서 할 필요는 없습니다. 클라우드를 계속 쓰면 비용·사용시간·권한·민감 데이터 외부 반출 문제가 생깁니다.

구분DGX Spark 역할경제 효과
개발 초기로컬에서 아이디어·기능 검증클라우드 비용 절감, 실패를 빨리·싸게 경험
중간컨테이너 그대로 관리, 코드+환경 함께 이동서버 이전 시 재구성 비용 감소 (호환성 유지)
확장사용자·데이터 증가 시 상위 GPU 환경으로 자연 이동엔비디아 입장: GPU 판매 + CUDA·NIM·Blueprint·Workbench 생태계 락인(Lock-in)
큰 그림 요약
DGX Spark 1대가 데이터센터를 대체하는 게 아니라 진입 지점을 개인에게 가져오는 것. 개발자는 DGX Spark에서 시작하지만 프로젝트가 커질수록 더 큰 NVIDIA GPU 환경으로 이동. 엔비디아가 확장하려는 것은 GPU 개수가 아니라 CUDA·컨테이너·NIM·Blueprint·Workbench·에이전트 프레임워크까지 포함한 소프트웨어 생태계입니다. GTC Taipei에서 발표된 RTX Spark가 Windows 소비자 쪽, DGX Spark가 Linux 개발자 쪽으로 전방위 확장을 담당합니다.

03. TWO PROBLEMS

하네스가 풀려는 2가지 문제

문제 1: 컨텍스트 부패 (Context Rot)

AI가 한 번에 볼 수 있는 정보량 = 컨텍스트 창 (책에서 한 번에 펼칠 수 있는 페이지 수). 작업이 길어지면 창이 꽉 차서 앞 내용을 잊습니다.

📖 컨텍스트 창 시뮬레이터

작업량35%

35% - 아직 괜찮음. 앞 대화 기억함.

엔트로픽 실험: 최전선 모델 Claude에 claude.ai 클론 시키자 ① 모든 걸 한 번에 하려다 컨텍스트 바닥나서 절반만 구현, 다음 세션에서 기억 못해 처음부터 다시 ② 어느 정도 진행 후 "다 됐네" 하고 조기 종료 선언.

문제 2: 규칙·울타리 문제

정보 문제가 아니라 절대 하면 안 되는 행동을 막는 구조적 제약이 없는 문제. 예: 결제 시스템 만들라 했는데 DB 테이블을 삭제해버림.

❌ 프롬프트 방식 (부탁)

"DB 삭제하지 마" 라고 말로 부탁. AI는 또 할 수 있음. 강제가 아님.

✅ 하네스 방식 (강제)

삭제 자체가 불가능한 구조 설계. 공장의 안전문처럼 구조로 막음.

06. THREE PILLARS

하네스의 3대 기둥

📄 컨텍스트 파일 (agent.md / claude.md)

AI가 가장 먼저 읽는 지도. 원칙: 1000페이지 설명서가 아니라 지도를 줘라. 60줄 이하로 보편적·항상 적용되는 내용만. 세부사항은 다른 파일에 나눠 필요할 때만 가져오기.

고스티(Ghostty) agent.md에는 에이전트가 저지른 실수를 한 줄씩 적어둠. 처음부터 완벽한 게 아니라 실패할 때마다 한 줄씩 추가되며 진화.

⚙️ 자동 강제 시스템

"좋은 코드 짜줘" 부탁이 아니라 기계적으로 강제.

  • 린터(Linter): 코드 맞춤법 검사기. 규칙 어기면 빨간 줄·에러 자동
  • 프리커밋 훅(Pre-commit Hook): 저장 버튼 누르는 순간 "잠깐 확인하고 저장해" 검사
  • 자동 교정 루프: 린터가 빨간불 → 에이전트가 스스로 수정. 사람 개입 0

원칙: 성공은 조용히, 실패만 시끄럽게. 테스트 통과하면 아무 말 안 함. 실패했을 때만 알림. 4천 줄 로그 다 보여주면 AI가 그걸 읽느라 할 일 못함.

🧹 가비지 컬렉션 (쓰레기 청소)

원래 프로그래밍에서 안 쓰는 메모리 자동 청소 개념. 여기서는 AI가 만든 나쁜 코드·문서 불일치·안 쓰는 코드를 주기적으로 청소하는 에이전트.

왜 필요? 기존 코드에 나쁜 패턴 있으면 AI가 그대로 따라해서 눈덩이처럼 불어남.

진화 방식: 에이전트가 실수할 때마다 그 실수는 새 규칙이 됨 → 린트 규칙 추가, 테스트 추가, 제약 추가. 말이 넘으려던 울타리가 점점 높아져 같은 실수 불가능.

08. FUTURE

앞으로 하네스는 어떻게 될까?

  • Richard Sutton (강화학습 창시자): 모델이 똑똑해질수록 하네스는 더 단순해져야 함. 하드코딩 규칙 추가하면 흐름 거스르는 것.
  • 셀프 하네스: 언젠가 에이전트가 스스로 "일 잘하기 위한 환경부터 설정할게요" 하고 하네스를 짤 것.
  • 템플릿화: 지금 서비스 템플릿 가져다 쓰듯, 앞으로는 "이 기술 스택용 하네스 템플릿"이 제공. 프레임워크 선택 기준이 개발자 경험→좋은 하네스 보유 여부로 바뀔 수도.
  • 모델이 똑똑해질수록 하네스 일부는 모델에 흡수되지만, 잘 구성된 환경+적절한 도구+검증은 어떤 에이전트든 더 효과적.
개발자 역할 변화: 코드 작성하는 선수 → 전술 짜고 팀 운영하는 감독. Chad Fowler가 말한 엄밀함의 재배치: 코드 한 줄 정확히 짜던 엄밀함이, 에이전트가 올바르게 동작하는 시스템을 설계하는 엄밀함으로 옮겨감. 더 높은 차원의 기술이 요구됨.
